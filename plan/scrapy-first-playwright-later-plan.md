# Design: Scrapy-first, Playwright-later Startup Research Pipeline

Generated by /office-hours on 2026-05-31
Branch: master
Repo: job-mcp
Status: DRAFT
Mode: Builder

## Problem Statement

The dashboard currently researches startups one company at a time or in small FastAPI background batches using `httpx` + BeautifulSoup in `startup_search/research.py`. That is good for quick checks, but it is too thin for researching all ~1.5k startups: there is no durable queue, no crawl-level progress, limited retry/rate-limit behavior, and no clean fallback path for JavaScript-heavy careers pages.

We want a crawler architecture that confirms AI-native product evidence and hiring evidence at scale while staying local, cheap, polite, and inspectable.

## What Makes This Cool

The win is not “scrape more pages.” The win is turning a mostly unverified spreadsheet into an evidence-backed internship target list where each high-ranked company has:

- fetched homepage/careers text,
- proof of AI-native product language,
- proof or absence of hiring evidence,
- confidence/debug status,
- best evidence URLs,
- and a clear reason it deserves outreach.

The crawler should make the dashboard feel less like a spreadsheet viewer and more like a research assistant that steadily improves its own data.

## Constraints

- Local-first. No paid scraping service required.
- Frugal. No LLM calls during crawling.
- Evidence-based. `Hiring = Yes` requires fetched page evidence.
- Source-aware scoring. Sheet-only AI signals stay capped until website confirmation.
- Polite crawling. Avoid hammering startup websites or triggering blocks.
- Incremental. Keep the existing Research button working while adding batch infrastructure.
- Playwright later, not first. Browser rendering is expensive and should only handle pages Scrapy cannot extract.

## Current System

Relevant files:

- `startup_search/research.py`: async `httpx` fetcher, homepage + hardcoded careers paths, returns `ResearchResult`.
- `startup_search/app.py`: `/api/research` queues FastAPI background batch, `/api/startups/{id}/research` researches one row.
- `startup_search/storage.py`: SQLite persistence and CSV export.
- `startup_search/scoring.py`: deterministic evidence scoring.
- `startup_search/static/app.js`: dashboard buttons and evidence display.

Current crawler behavior:

1. Normalize company website.
2. Fetch homepage.
3. Fetch `/careers`, `/jobs`, `/join-us`, `/company/careers`.
4. Extract visible-ish text via BeautifulSoup.
5. Score all fetched text deterministically.
6. Save evidence URLs and scores.

## Premises

1. Scrapy should become the batch crawler engine, not the single-row Research implementation at first.
   - Reason: the current single-row path is useful for interactive dashboard feedback and should remain simple.

2. Playwright should be a fallback only after Scrapy reports low text, suspicious empty content, or blocked/JS-heavy pages.
   - Reason: browser crawling 1.5k companies by default is slow and likely to trigger more blocking.

3. The unit of work should be a company research job, not a raw URL crawl.
   - Reason: scoring needs a company-level bundle of homepage + careers + discovered job links.

4. The database needs crawl status metadata before “Research all” exists.
   - Reason: without status, retries, progress, and failures become invisible.

5. We should keep deterministic scoring unchanged as the contract.
   - Reason: crawler improvements should feed better evidence into the existing scoring model, not rewrite ranking logic at the same time.

## Alternatives Considered

### Approach A: Minimal viable Scrapy batch command

Summary: Add a standalone Scrapy spider that reads unverified startups from SQLite, crawls homepage + known careers paths, then writes `ResearchResult` back through existing storage/scoring functions.

Effort: M
Risk: Low-Med

Pros:
- Fastest path to researching all 1.5k rows outside the web request lifecycle.
- Reuses `deterministic_research()` and `apply_research()` without changing dashboard scoring semantics.
- Easy to run manually from the conda env with a CLI command.

Cons:
- Progress UI remains basic unless we add job-status tables.
- If interrupted, resume logic depends on existing `research_confidence`, which is coarse.
- JS-heavy careers pages still fail until fallback is added.

Reuses:
- `StartupInput`, `ResearchResult`
- `deterministic_research()`
- `apply_research()`
- existing evidence URL conventions

### Approach B: Durable research queue + Scrapy worker

Summary: Add explicit SQLite tables for `research_jobs`, `research_fetches`, and optional `research_runs`. The dashboard enqueues work, a Scrapy worker drains it, and the UI polls progress.

Effort: L
Risk: Med

Pros:
- Best foundation for “Research all unverified,” pause/resume, retries, and progress bars.
- Makes failures inspectable by URL/status/error, not hidden inside one confidence number.
- Cleanly supports a later Playwright fallback queue.

Cons:
- More schema and UI work before visible crawling improvements land.
- Requires careful job state transitions to avoid stuck/racey jobs.
- Slightly overbuilt if this remains a one-off personal dashboard.

Reuses:
- Existing startup table as source of truth.
- Existing scoring and export pipeline.
- Current dashboard filter/sort model.

### Approach C: Hybrid local crawler service

Summary: Run a separate local crawler service or process manager that owns crawling, exposes `/crawler/status`, and lets FastAPI start/stop jobs. Scrapy is the first worker backend; Playwright becomes a second backend.

Effort: XL
Risk: High

Pros:
- Clean separation between dashboard app and crawler runtime.
- Best long-term path if this grows into a reusable research product.
- Easier to add concurrency controls, worker health, and logs.

Cons:
- Too much architecture for the current personal internship-search tool.
- More moving parts to run locally.
- Slower to reach the practical goal: better verified company rankings.

Reuses:
- Existing FastAPI API/UI as the operator surface.
- Existing scoring functions as post-processing.

## Recommended Approach

Choose **Approach B: Durable research queue + Scrapy worker**, implemented in two phases.

The temptation is Approach A because it is faster, but the user asked why we do not research everything by default. The honest answer is reliability and observability. A durable queue fixes that. It lets the app say: “892 done, 411 pending, 138 failed, 64 need browser fallback,” instead of just firing a background task and hoping it finishes.

## Implementation Plan

### Phase 1: Scrapy-first batch crawler, no Playwright yet

Goal: Research all unverified companies with static HTML crawling and visible progress.

#### 1. Add crawler dependencies

Add to project environment/docs:

- `scrapy`
- optionally `tldextract` for domain normalization

Do not add `scrapy-playwright` yet.

#### 2. Add durable queue schema

Add SQLite tables through `storage.py` or a small migration helper:

```sql
CREATE TABLE IF NOT EXISTS research_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  status TEXT NOT NULL,
  total INTEGER NOT NULL DEFAULT 0,
  completed INTEGER NOT NULL DEFAULT 0,
  failed INTEGER NOT NULL DEFAULT 0,
  needs_browser INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS research_jobs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id INTEGER,
  startup_id INTEGER NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',
  attempts INTEGER NOT NULL DEFAULT 0,
  last_error TEXT,
  needs_browser INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(run_id, startup_id)
);

CREATE TABLE IF NOT EXISTS research_fetches (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  job_id INTEGER NOT NULL,
  url TEXT NOT NULL,
  final_url TEXT,
  status_code INTEGER,
  content_type TEXT,
  text_chars INTEGER NOT NULL DEFAULT 0,
  error TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Keep this deliberately small. Do not build a generic crawler database.

#### 3. Define job states

Use simple string states:

- `pending`
- `running`
- `completed`
- `failed`
- `needs_browser`
- `skipped`

A company becomes `needs_browser` when:

- homepage returns mostly empty text,
- careers page returns mostly empty text,
- content looks like a JS app shell,
- all likely careers URLs 404 but homepage has links suggesting jobs/careers that Scrapy could not extract,
- response status indicates likely bot/blocking but browser may succeed.

#### 4. Create a Scrapy project under `startup_search/crawler/`

Suggested structure:

```text
startup_search/crawler/
  __init__.py
  items.py
  pipelines.py
  settings.py
  spiders/
    __init__.py
    startup_research_spider.py
```

The spider should not invent scoring. It should collect text + evidence URLs and hand a company-level bundle to the same scorer.

#### 5. Spider input

The spider reads jobs from SQLite:

- default: pending jobs for the latest active run,
- optional CLI arg: `run_id`,
- optional CLI arg: `limit`,
- optional CLI arg: `startup_id` for debugging.

Example command:

```bash
conda run -n startup-search scrapy crawl startup_research -a run_id=1 -a limit=100
```

Better ergonomic wrapper later:

```bash
conda run -n startup-search python -m startup_search.crawler run --limit 100
```

#### 6. URL strategy

For each company:

- homepage from sheet,
- known careers paths:
  - `/careers`
  - `/jobs`
  - `/join-us`
  - `/company/careers`
  - `/work-with-us`
  - `/positions`
  - `/open-roles`
- links discovered from homepage containing:
  - careers
  - jobs
  - join
  - hiring
  - lever.co
  - greenhouse.io
  - ashbyhq.com
  - workable.com
  - wellfound.com

Limit per company:

- max 8 pages in Phase 1,
- max 2 external ATS domains,
- max text chars per page follows existing `settings.max_page_chars`.

#### 7. Politeness defaults

Scrapy settings:

```python
ROBOTSTXT_OBEY = True
CONCURRENT_REQUESTS = 16
CONCURRENT_REQUESTS_PER_DOMAIN = 1
DOWNLOAD_DELAY = 0.5
RANDOMIZE_DOWNLOAD_DELAY = True
DOWNLOAD_TIMEOUT = 12
RETRY_TIMES = 2
AUTOTHROTTLE_ENABLED = True
AUTOTHROTTLE_START_DELAY = 0.5
AUTOTHROTTLE_MAX_DELAY = 8
USER_AGENT = 'StartupSearchBot/0.2 (+local research dashboard; contact: local)'
```

Since this is local personal research, keep crawling polite and bounded.

#### 8. Company-level aggregation

The spider should aggregate fetched pages by `startup_id`:

```python
CompanyResearchBundle(
  startup=StartupInput(...),
  pages=[FetchedPage(url, final_url, status, text, source_type)],
  errors=[...],
)
```

Then call:

```python
result = deterministic_research(startup, combined_text, evidence_urls)
apply_research(startup_id, result)
```

Also write `research_fetches` rows for debugging.

#### 9. FastAPI endpoints

Add endpoints:

- `POST /api/research-runs`
  - creates jobs for unverified rows, returns `run_id`.
- `GET /api/research-runs/{run_id}`
  - returns counts and recent failures.
- `POST /api/research-runs/{run_id}/cancel`
  - marks pending jobs skipped/cancelled. Worker checks state between jobs.

Keep existing endpoints:

- `POST /api/startups/{id}/research` should still do quick single-company research.
- `POST /api/research` can become a compatibility wrapper that creates a run.

#### 10. Dashboard UI

Add a small “Research queue” panel:

- `Research all unverified`
- `Research next 100`
- progress: completed / total
- failed count
- needs browser count
- last updated
- button: export CSV after run

Do not build a full job dashboard yet. The user needs trust and progress, not admin software.

#### 11. Tests

Add tests for:

- queue creation only includes unverified/low-confidence rows,
- completed Scrapy bundle updates startup score via existing scorer,
- failed fetch records do not mark hiring `Yes`,
- JS-empty page is marked `needs_browser`,
- discovered ATS/careers links are included as evidence URLs when text is useful.

Success criteria:

- `pytest` passes.
- A run of 10 companies completes locally.
- A run can be interrupted and resumed without duplicating completed companies.
- CSV export shows updated evidence after the run.

### Phase 2: Better static extraction before browser fallback

Goal: squeeze more value from Scrapy before paying the Playwright cost.

Add special static extractors for common ATS systems:

- Greenhouse job board pages,
- Lever postings pages,
- Ashby job board pages,
- Workable pages.

Why before Playwright: many ATS pages expose useful HTML or JSON if called directly. If we handle those URLs well, fewer companies need browser fallback.

Success criteria:

- Known ATS pages return role titles and locations.
- Hiring evidence includes concrete role/category text.
- Fewer jobs land in `needs_browser`.

### Phase 3: Playwright fallback queue

Goal: handle only the leftovers Scrapy cannot parse.

Add dependency:

- `scrapy-playwright` or a separate local Playwright worker.

Preferred first version: **separate Playwright fallback worker**, not mixed into every Scrapy request.

Reason: it keeps the fast path fast and makes browser usage explicit.

Flow:

1. Scrapy marks job `needs_browser` with reason.
2. User clicks `Run browser fallback` or worker runs fallback for N jobs.
3. Playwright fetches homepage/careers pages, waits for network idle or key selectors, extracts text.
4. Same scorer updates the row.
5. Job becomes `completed` or `failed_browser`.

Playwright fallback triggers:

- text chars below threshold, e.g. `< 500`,
- title/body says “enable JavaScript,”
- React/Next shell with almost no content,
- Cloudflare or bot page that may still render locally,
- Careers link exists but static response empty.

Playwright limits:

- max 2 browser pages per company initially,
- max 20 fallback companies per run unless user opts in,
- screenshots only for debug failures, not by default.

### Phase 4: Evidence quality and ranking polish

Goal: make the data more trustworthy after the crawler works.

Add fields or derived labels:

- `research_source`: `sheet_only`, `static_scrape`, `browser_scrape`
- `research_status`: user-visible status
- `last_researched_at`
- `research_error_summary`
- `best_hiring_url`
- maybe `best_ai_evidence_url`

Dashboard copy:

- “Confirmed from website”
- “Static scrape found no AI-native evidence”
- “Needs browser fallback”
- “Careers page found, no relevant roles”

## Non-goals

- No LLM-based site classification during crawling.
- No proxy rotation.
- No paid scraping APIs.
- No full web crawling beyond company homepage/careers/job pages.
- No outreach generation during batch research.
- No replacing the current scoring formula during crawler work.

## Open Questions

1. Should `robots.txt` be obeyed strictly? Recommendation: yes for default local use.
2. Should the crawler contact external ATS domains? Recommendation: yes, but only when linked from the company homepage/careers page.
3. Should browser fallback be automatic? Recommendation: not initially. Make it a separate button so the user sees cost/time.
4. Should failed companies be hidden? Recommendation: no. Show them as “needs review” or “failed research.”

## Success Criteria

A good first implementation is done when:

- User can click `Research all unverified`.
- Dashboard shows live-ish progress.
- Scrapy researches at least 100 companies without tying up a browser.
- Interrupted runs can resume.
- Companies with website-confirmed AI language rise above the sheet-only cap.
- Hiring `Yes` only appears with fetched evidence and a visible link.
- `needs_browser` companies are separated for later fallback.
- Tests cover queue selection, update behavior, and failure handling.

## Recommended Build Order

1. Add queue tables and storage helpers.
2. Add queue API endpoints.
3. Add Scrapy dependency and spider skeleton.
4. Make spider process one company end-to-end.
5. Add aggregation + scoring + persistence.
6. Add progress UI.
7. Add tests.
8. Run 10-company smoke test.
9. Run 100-company batch.
10. Only then design Playwright fallback.

## The Assignment

Before implementation, pick 20 representative companies from the current DB:

- 5 known AI-native sites,
- 5 sheet-only AI-looking sites,
- 5 companies likely hiring,
- 5 weird/JS-heavy/broken sites.

Use them as the crawler evaluation set. If Scrapy handles most of these cleanly, proceed. If half are JS-heavy or blocked, bring Playwright forward earlier.

## What I noticed

- The user is correctly insisting that sheet metadata is not enough. That pushed the system from “ranking spreadsheet” toward “evidence-backed research.”
- The right architecture is not “Scrapy instead of Playwright.” It is “cheap static proof first, expensive browser proof only when needed.”
- The strongest product move is progress visibility. Researching everything by default is fine only after the app can explain what it is doing and what failed.
